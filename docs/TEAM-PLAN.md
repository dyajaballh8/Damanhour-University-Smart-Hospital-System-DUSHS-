# خطة عمل فريق DUSHS

## هدف المشروع

بناء نظام متكامل لإدارة مستشفى جامعة دمنهور، مع دمج ميزة ذكاء اصطناعي أساسية لتوقع وقت انتظار المرضى. يتكون الفريق من ثلاثة أعضاء: Backend، Frontend، وAI. لكل عضو مسؤولية واضحة، مع اتفاق مشترك على المتطلبات والعقود التي تربط الأجزاء.

## النطاق الأساسي للعرض

يجب أن يدعم النظام رحلة مريض قابلة للعرض من البداية للنهاية:

1. موظف الاستقبال يسجل المريض أو يبحث عن ملفه.
2. يحجز موعدًا في قسم مناسب، مع منع تعارض المواعيد.
3. يسجل حضور المريض ويضيفه إلى قائمة الانتظار.
4. يعرض النظام توقع وقت الانتظار.
5. الطبيب يراجع بيانات المريض ويسجل ملخص الزيارة.
6. تعرض الإدارة مؤشرات تشغيلية أساسية.

الأقسام الإضافية مثل المعمل والأسِرّة والصيدلية والمخزون تُنفذ حسب الوقت المتاح، بعد استقرار الرحلة الأساسية.

## قرارات مشتركة قبل بدء التنفيذ

يتفق أعضاء الفريق ويكتبون القرارات في مجلد `docs/`:

- الأدوار الأساسية: مريض، استقبال، طبيب، وإدارة. تُضاف أدوار التمريض والمعمل والصيدلية عند الحاجة.
- التقنيات المستخدمة للواجهة والـBackend وقاعدة البيانات.
- طريقة تشغيل خدمة AI محليًا وربطها بالـBackend.
- أسماء الحقول وأنواعها وأشكال الاستجابات والأخطاء.
- الحد الأدنى المطلوب للعرض، وما يمكن تأجيله.
- مصدر البيانات الاصطناعية وطريقة تقييم نموذج AI.

يُعتمد **توقع وقت الانتظار** كميزة AI الأساسية، ولا تُستخدم بيانات مرضى حقيقية في التطوير أو العرض.

## العضو الأول: Backend وقاعدة البيانات

### المسؤوليات

- تصميم قاعدة البيانات وتنفيذها للكيانات الأساسية: المستخدمون، المرضى، الأطباء، الأقسام، المواعيد، الزيارات، وقائمة الانتظار.
- تنفيذ تسجيل الدخول والتحقق من الدور والصلاحيات داخل Backend.
- إنشاء APIs للمرضى والأطباء والأقسام والمواعيد والحضور وقائمة الانتظار والزيارات.
- منع تعارض المواعيد والتحقق من صحة المدخلات.
- ربط Backend بخدمة AI وتمرير مدخلات التوقع وإرجاع نتيجته للواجهة.
- إضافة بيانات تجريبية وتعليمات تشغيل Backend وقاعدة البيانات.

### التسليمات

- مخطط قاعدة البيانات وملفات migrations أو خطوات إعدادها.
- APIs موثقة في `docs/api/API.md`.
- Backend يعمل محليًا مع بيانات تجريبية وحسابات للأدوار الأساسية.
- استجابات واضحة للنجاح والتحقق من الأخطاء وعدم كفاية الصلاحيات.

### معيار القبول

يمكن للواجهة تسجيل مريض، إنشاء موعد، تسجيل الحضور، عرض بيانات قائمة الانتظار، وتسجيل ملخص الزيارة. يرفض Backend المواعيد المتعارضة والطلبات غير المصرح بها.

## العضو الثاني: Frontend

### المسؤوليات

- إعداد بنية الواجهة والتنقل الموحد بين الصفحات.
- تنفيذ تسجيل الدخول ولوحات الاستخدام المناسبة للأدوار.
- بناء شاشات المرضى وتفاصيل الملف، الأطباء والأقسام، المواعيد، الحضور وقائمة الانتظار، وتسجيل الزيارة.
- ربط الشاشات بالـAPIs المتفق عليها.
- عرض حالات التحميل والأخطاء والبيانات غير المتاحة.
- عرض توقع الانتظار ومستوى الازدحام، مع توضيح أنه توقع مساعد.

### التسليمات

- واجهات قابلة للتشغيل لسيناريو العرض الأساسي.
- ربط شاشات المرضى والمواعيد والانتظار بالـBackend.
- عرض نتائج AI الواردة من Backend دون إجراء حسابات محلية بديلة.
- تعليمات تشغيل الواجهة.

### معيار القبول

يستطيع المستخدم إكمال رحلة المريض من الواجهة دون تعديل البيانات يدويًا في قاعدة البيانات. وتُحمى العمليات الحساسة من جانب Backend حتى لو أخفت الواجهة بعض الأزرار.

## العضو الثالث: AI

### المسؤوليات

- تحديد بيانات التنبؤ المطلوبة، مثل عدد المنتظرين، الأطباء المتاحين، وقت اليوم، يوم الأسبوع، ومتوسط مدة الكشف.
- إنشاء أو تجهيز بيانات اصطناعية مناسبة، مع توثيق أنها تجريبية.
- بناء baseline بسيط للمقارنة ثم تدريب نموذج مناسب لحجم البيانات.
- تقييم النموذج باستخدام MAE بالدقائق، وتوثيق طريقة تقسيم البيانات ونتائج المقارنة.
- توفير خدمة تنبؤ مستقلة يتصل بها Backend.
- توثيق طريقة التثبيت والتشغيل والمدخلات والمخرجات وحدود النموذج.

### التسليمات

- كود تجهيز البيانات والتدريب والتنبؤ والتقييم داخل `ai/src/`.
- بيانات تجريبية أو طريقة توليدها داخل `ai/data/`، دون بيانات شخصية.
- ملف الاعتماديات في `ai/requirements.txt`.
- توثيق في `ai/README.md` يشمل خطوات التشغيل ونتيجة التقييم.
- خدمة تنبؤ تستقبل الطلب المتفق عليه وتعيد استجابة ثابتة الشكل.

### معيار القبول

تعمل الخدمة على بيانات تجريبية، وتعيد توقعًا رقميًا صالحًا، مع تقييم MAE ومقارنة واضحة بالـbaseline. عند تعطل الخدمة، لا يعرض النظام رقمًا غير موثوق؛ تظهر حالة أن التوقع غير متاح.

## عقد الربط بين Backend وAI والواجهة

يتفق الفريق على صيغة الطلب والاستجابة قبل تنفيذ الربط. مثال مقترح:

طلب التنبؤ:

```json
{
  "departmentId": 3,
  "queueLength": 12,
  "activeDoctors": 2,
  "hour": 10,
  "dayOfWeek": 2
}
```

استجابة التنبؤ:

```json
{
  "expectedWaitMinutes": 35,
  "congestionLevel": "medium",
  "modelVersion": "1.0"
}
```

المسؤوليات في هذا الربط:

- AI يحدد المدخلات المطلوبة، ويحسب النتيجة، ويوثق النموذج.
- Backend يتحقق من الطلب، ويتصل بخدمة AI، ويتعامل مع أخطائها.
- Frontend يرسل الطلب من خلال Backend ويعرض النتيجة للمستخدم.

أي تغيير في أسماء الحقول أو أنواعها يجب الاتفاق عليه وتوثيقه قبل دمجه.

## طريقة العمل على GitHub

- يستخدم كل عضو فرعًا خاصًا بميزته، مثل:
  - `feature/backend-patients`
  - `feature/frontend-appointments`
  - `feature/ai-wait-time`
- تُرفع التغييرات في Pull Request إلى `main` وتُراجع قبل الدمج.
- لا يعدل عضو ملفات جزء يملكه عضو آخر دون تنسيق مسبق.
- تُوثق تغييرات عقد الـAPI في `docs/api/API.md` ويُبلغ بها الفريق.
- لا تُرفع ملفات `.env` أو كلمات المرور أو بيانات مرضى حقيقية. تُستخدم بيانات تجريبية فقط.
- تُكتب خطوات التشغيل لكل جزء في README الخاص به أو في README الرئيسي.

## مهام مشتركة للفريق

- مراجعة المتطلبات وUse Cases وERD معًا.
- الاتفاق على سيناريو العرض قبل بدء التنفيذ.
- اختبار رحلة المريض بعد دمج الأجزاء الثلاثة.
- مراجعة الصلاحيات وحماية البيانات.
- معالجة تعارضات الدمج ومشكلات التكامل.
- تجهيز العرض النهائي بحيث يوضح عمل النظام، طريقة تقييم AI، ومساهمة كل عضو.

## تعريف اكتمال المهمة

تُعد المهمة جاهزة عندما:

- تعمل على جهاز عضو آخر باتباع تعليمات التشغيل.
- تستخدم عقد البيانات المتفق عليه.
- تُراجع وتُدمج عبر Pull Request.
- تُجرب على بيانات اصطناعية.
- تُوثق طريقة تشغيلها وأي حدود أو افتراضات مهمة.

## ترتيب التنفيذ

1. الاتفاق على رحلة المريض والأدوار وعقد AI وAPI.
2. بدء تطوير Backend وFrontend وAI بالتوازي على العقود والبيانات المتفق عليها.
3. دمج تسجيل المريض والمواعيد والحضور وقائمة الانتظار.
4. ربط توقع وقت الانتظار من AI عبر Backend وعرضه في Frontend.
5. إضافة الزيارات والتقارير والوظائف الإضافية حسب الوقت.
6. اختبار النظام كاملًا وتجهيز بيانات العرض والتوثيق.
